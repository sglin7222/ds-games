沒學過程式也看得懂。先把名詞和定義弄清楚，後面的遊戲才不會霧煞煞。

一句話定義

DEFINITION · 定義
雜湊表（Hash Table）是一種資料的擺放方式：準備一排有編號的格子，再用一條固定的「雜湊函式」，從每筆資料的 key 直接算出它該住第幾格。

放的時候算一次，找的時候再算一次——算出來是第幾格，就直接去那一格，不用從頭一格一格翻。

這句話裡有好幾個沒聽過的詞——「key」、「格子」、「雜湊函式」。別急，下面一個一個拆。先記住雜湊表想解決的事情只有一件：

目的 資料一直放進來、一直有人問「某某在不在？」、偶爾還要刪掉。雜湊表讓這三件事平均都幾乎一步完成，不管裡面已經有幾萬筆。就像郵差分信：看信封上的規則（例如門牌號碼）就知道要投進第幾個信箱，領信的人也直接開自己那一格，不用把整棟樓的信箱都翻一遍。

先認識這些詞（照順序讀，後面的詞會用到前面的）

資料結構 data structure
「一堆資料要怎麼擺」的規則。擺法不同，找東西、放東西的速度就差很多。雜湊表就是其中一種擺法。
同樣一堆衣服，摺好分格放 vs. 全塞進一個袋子，找起來速度天差地遠。
陣列 / 索引 array / index
陣列是一排連在一起、有編號的格子，每格放一個資料。格子的編號叫「索引」，從 0 開始數。只要知道索引，就能一步打開那一格。
車站的置物櫃：報出「3 號櫃」，直接走過去打開，不用從 0 號開始一個一個試。
取餘數 % modulo
a % m 讀作「a 除以 m 的餘數」。例如 23 % 7 = 2，因為 23 = 7 × 3 + 2。重點：除以 7 的餘數一定是 0～6 其中一個，不會更大，也不會是負的。
一週 7 天：今天星期日（第 0 天），23 天後是星期幾？23 % 7 = 2 → 星期二。
鍵 / 值 key / value
key 是用來「認人」的那個東西，同一張表裡每個 key 只出現一次；value 是跟著 key 一起存的內容。本關為了簡單，只存 key（例如 10、17、cat），問題都是「這個 key 在不在表裡」。
通訊錄：名字是 key，電話號碼是 value。你用名字去查電話，不會用電話去查名字。
桶 / 格子 bucket / slot
雜湊表底下就是一個陣列，每一格叫一個「桶」。桶的數量寫成 m。本關一開始 m = 7，桶的編號是 0～6。
大樓一樓的 7 個信箱，編號 0 到 6。
雜湊函式 hash function
一條固定的計算規則：丟進一個 key，算出一個桶的編號（這個編號叫雜湊值）。本關用 h(key) = key % m。例如 m = 7 時，h(23) = 23 % 7 = 2，23 就住第 2 格。key 是文字的話，先把每個字母的內碼加起來變成數字："cat" = 99 + 97 + 116 = 312，312 % 7 = 4。也有書寫成「雜湊函數」，是同一個東西。
分信機：信丟進去，它看門牌號碼，吐出「投第幾號信箱」。同一封信丟幾次，答案永遠一樣。
雜湊表 hash table
把上面兩樣東西組在一起：m 個桶＋一條雜湊函式。放資料時用函式算出桶號、放進去；找資料時再算一次，只看那一桶。它永遠只看自己該去的那一桶，其他桶完全不碰。
郵差和住戶都照同一套規則找信箱，所以信永遠在「算得出來」的那一格。
碰撞 collision
兩個不同的 key 算出同一個桶號。例如 m = 7 時，10 % 7 = 3，17 % 7 = 3——兩個都要住第 3 格。
兩家人門牌不同，卻被分到同一個信箱。
鴿籠原理 pigeonhole principle
鴿子比籠子多，就一定有一個籠子擠了兩隻以上。key 可能的值有無限多，桶只有 m 個，所以碰撞一定會發生，不是程式寫錯。雜湊表要煩惱的不是「怎麼不撞」，而是「撞了怎麼辦」。
8 個人要擠進 7 間房，不管怎麼分，至少有一間住了 2 人。
鏈結法 chaining
碰撞的第一種解法（左表）：每個桶掛一條鏈條（一節一節串起來，每一節記著「下一節在哪」，可以一直接下去）。撞到同一桶的資料全部串在那條鏈上。本關把新來的掛在鏈的最前面。
信箱塞不下，就在信箱下面掛一串夾子，信一封一封夾上去。
開放定址 / 線性探測 open addressing / linear probing
碰撞的第二種解法（右表）：一格只住一筆。算出來的格子被佔了，就往下一格看（h+1、h+2……，走過第 6 格就繞回第 0 格），遇到的第一個空格就住下。這種「一格一格往下找」叫線性探測，走過的格子叫探測路徑。
電影院你的位子被坐了，就往右邊一個一個找，坐第一個空位。
墓碑 tombstone
開放定址刪資料時，不能把格子清空，要留一個「這裡曾經有人住」的記號。因為查找是「沿路走到空格才停」，清空會把別人的探測路徑從中間弄斷。墓碑的意思是：這格現在沒人，但路還沒斷，請繼續往下找。
店搬走了，門口貼「本店已遷移，往前直走」，而不是把整條路封起來。
載入因子 α load factor
α = n ÷ m，n 是目前存了幾筆，m 是桶數，白話就是「表有多滿」。例如 7 格放了 5 筆，α = 5 ÷ 7 ≈ 0.71。α 越大越容易撞、找得越久。本關的警戒線是 0.7。也有書叫它「負載因子」。
停車場的滿載率：越滿，越要繞好幾圈才找得到位子。
重新雜湊 rehash
表太滿時，換一個更大的表（本關：桶數翻倍再取質數，7 → 17），然後每筆資料用新的 m 重算一次桶號、重新放。例如 22：舊表 22 % 7 = 1，新表 22 % 17 = 5，就搬去第 5 格。
公司人太多，搬到更大的辦公室，每個人照新的座位表重新入座。
O(1)、O(n)，平均 vs 最壞 Big-O 記號
描述「資料變多時，工作量怎麼跟著變多」，n 是資料的數量。O(1)：不管資料多少，步數都差不多固定。O(n)：資料多一倍，工作也多一倍。雜湊表平均 O(1)（資料撒得勻、表不太滿時），但最壞 O(n)（所有 key 都撞進同一桶時，只好一筆一筆翻）。
平均：每個信箱只有一兩封信，一眼就找到。最壞：全棟的信都塞進同一個信箱，只能一封一封翻。

定義拆成三個零件：缺一個就不是雜湊表

  1. 一排桶——一個有 m 格的陣列（本關 m = 7，編號 0～6）。
  2. 雜湊函式——把 key 變成桶號的固定規則（本關 key % m）。
  3. 碰撞處理規則——兩個 key 搶同一格時怎麼辦（本關左表用鏈結法，右表用線性探測）。

容易搞混的幾件事

常被搞混的說法對嗎？真相
「雜湊表跟陣列是兩種完全不同的東西」不對雜湊表底下就是一個陣列。差別是：陣列要你自己給索引；雜湊表用雜湊函式從 key 算出索引。
「雜湊值就是資料本身」不對雜湊值只是「桶號」。10 和 17 的雜湊值都是 3，但它們是兩筆不同的資料，所以找到第 3 格之後，還要逐一比對才知道是不是你要的那筆。
「發生碰撞代表程式寫錯了」不對鴿籠原理：key 比桶多，碰撞一定會發生。好的雜湊函式只是讓碰撞少而且平均，不是零。
「雜湊表裡的資料有照大小排好」不對資料住哪格只看 key % m，跟大小順序無關。例如 m = 7 時，20 住第 6 格，而比它大的 23 住第 2 格。想要排好順序，要用別的資料結構（例如第 11 關的二元搜尋樹）。
「開放定址刪除＝把那格清空」不對要放墓碑。清空會把探測路徑從中間弄斷，被擠到後面的資料就找不到了。鏈結法才是直接把那一節摘掉就好。
「雜湊表平均 O(1)」對，但有條件前提是雜湊函式撒得勻、α 不太大。全部撞進同一桶時就退化成最壞 O(n)。「永遠 O(1)」是錯的。

自我檢查（先自己想，再點開看答案）

m = 7，空表依序放入 9、30。各算出第幾格？會碰撞嗎？兩種解法最後各長什麼樣？
9 = 7 × 1 + 2，9 % 7 = 2；30 = 7 × 4 + 2，30 % 7 = 2。兩個都是第 2 格，會碰撞。鏈結法：第 2 格的鏈變成 30 → 9（新來的掛最前面）。線性探測：9 住第 2 格，30 發現第 2 格被佔，往下看第 3 格是空的，住第 3 格。
表有 7 格，放了 8 筆不同的 key，一定會碰撞嗎？只放 2 筆有可能碰撞嗎？
放 8 筆一定會：8 隻鴿子進 7 個籠子，至少一籠有 2 隻（鴿籠原理）。只放 2 筆也有可能：例如 10 和 17，% 7 都是 3。碰撞跟「表滿不滿」無關，只是越滿越常發生。（順帶一提：開放定址一格只住一筆，7 格最多放 7 筆，第 8 筆根本放不進去，一定要先 rehash。）
7 格的表放了 5 筆，載入因子 α 是多少？有沒有超過本關的警戒線？rehash 成 17 格之後呢？
α = 5 ÷ 7 ≈ 0.71，超過 0.7 警戒線，該擴桶了。rehash 成 17 格後，α = 5 ÷ 17 ≈ 0.29，表變得很空，碰撞和探測都會變少。
m = 7，依序放入 7、14、21、28，查 28 要看幾筆？這說明了什麼？
7、14、21、28 都是 7 的倍數，% 7 全部等於 0，全擠進第 0 格。鏈結法：第 0 格的鏈是 28 → 21 → 14 → 7，查 28 剛好在第 1 節，看 1 筆；但如果查的是最早放的 7，要翻完整條鏈看 4 筆。線性探測：它們住第 0、1、2、3 格，查 28 要走 0 → 1 → 2 → 3，看 4 格。這就是最壞 O(n)：所有 key 撞在一起，雜湊表就退化成一筆一筆翻。所以雜湊函式要撒得勻、資料不能剛好跟 m 有規律。

怎麼玩

畫面上有兩張表，各有 7 個編號 0～6 的格子（桶）。每筆資料先經過「雜湊函式」key % 7（除以 7 取餘數）算出該住第幾格——像郵差按姓氏筆畫把信分進 7 個信箱。兩家人被分到同一個信箱，就是碰撞：左表把他們串成鏈，右表讓後到的往下找空房。

演示模式

  1. 挑一個關卡，或自己輸入操作序列（+10 插入、?10 查找、-10 刪除、! 擴桶）。
  2. 按 下一步：先看雜湊值怎麼算，再看兩張表各自怎麼反應。
  3. 碰撞發生時該格會標「碰撞!」，右表的探測路徑會留下編號腳印 ①②③。
  4. 盯著右側欄的 α 載入因子：超過紅線 0.7，右表的腳印會開始一長串。

闖關模式

  1. 先不給答案，由你算：這個 key 會落在哪一格？會不會碰撞？最後住哪？查找要看幾格？
  2. 答對得分，連續答對額外加分；答錯立刻說明正確答案和理由。
操作 鍵盤 → 下一步、← 上一步、空白鍵 播放／暫停。

你會學到什麼

  • 雜湊函式在做什麼 —— 把任意大的 key 壓進 0～m-1 的格子編號；為什麼取餘數 %、為什麼桶數挑質數。
  • 碰撞為什麼必然發生 —— 格子比可能的 key 少，總有兩家人分到同一個信箱（鴿籠原理）。
  • 兩種解法的哲學 —— 鏈結法「往外掛鏈子」vs 開放定址「往下擠房間」，同一串資料並排比較。
  • 開放定址的刪除陷阱 —— 直接清空會讓後面的探測斷路，必須放墓碑 🪦。本頁會演這個反例。
  • 載入因子 α = n/m —— 為什麼 α 一過 0.7 開放定址明顯變慢，以及 rehash 怎麼救回來。
  • 為什麼平均 O(1)、最壞 O(n) —— 「雜湊表永遠 O(1)」是誤解，第 03 段拆給你看。
建議順序 先玩「大塞車」看兩邊怎麼處理碰撞，再玩「刪除陷阱」看墓碑為什麼非放不可，最後玩「塞爆再擴桶」看 α 曲線飆高與 rehash。

    整份程式逐行白話說明（寫給完全沒學過程式的你）

      這個遊戲跑的程式（完整版）

      把視覺化全部拿掉，鏈結法雜湊表的本體就是這樣——插入、查找、刪除，外加 α 超標時自動擴桶：

      #include <vector>
#include <list>
using namespace std;

int nextPrime(int x) {                       // 找 ≥ x 的第一個質數
    for (;; ++x) {
        bool p = x > 1;
        for (int d = 2; d * d <= x; ++d) if (x % d == 0) p = false;
        if (p) return x;
    }
}

struct HashTable {
    int n = 0;                               // 目前存了幾筆
    vector<list<int>> b;                     // m 個桶，每桶掛一條鏈
    HashTable(int m = 7) : b(m) {}

    int H(int key) const { return key % (int)b.size(); }  // 雜湊函式

    bool find(int key) const {
        for (int x : b[H(key)])              // 只翻自己那一桶的鏈
            if (x == key) return true;
        return false;
    }
    void insert(int key) {
        if (find(key)) return;               // 已存在就不重複放
        b[H(key)].push_front(key);
        if (++n > 0.7 * b.size()) rehash();  // α 超過 0.7 → 擴桶
    }
    void erase(int key) {
        b[H(key)].remove(key);               // 把節點從鏈上摘掉
        --n;                                 //（假設 key 原本存在）
    }
    void rehash() {                          // 桶數翻倍取質數，全部重新安家
        vector<list<int>> old = move(b);
        b.assign(nextPrime(2 * (int)old.size()), {});
        for (auto& chain : old)
            for (int x : chain) b[H(x)].push_front(x);   // 用「新的 m」重算
    }
};

      核心不到二十行。遊戲頁面多出來的幾百行，全是為了「讓碰撞看得見」——包括右邊那張本體程式裡根本不存在的開放定址表（它的版本在第 03 段）。

      03

      這個功能是怎麼做到的

      從「為什麼要雜湊」走到「碰撞怎麼收拾」，每個設計為什麼非要不可。

      問題定義

      我們想要一個櫃子：放東西、找東西、刪東西，三件事都幾乎瞬間完成——不管櫃子裡已經有幾萬筆。先看看手上已有的工具差在哪：

      操作未排序陣列排序陣列雜湊表
      查找 key 在不在O(n) 逐格翻O(log n) 二分平均 O(1)
      插入一筆O(1) 塞尾巴O(n) 要挪位平均 O(1)
      刪除一筆O(n) 先找到O(n) 要補洞平均 O(1)

      三個 O(1) 不是免費的：代價是碰撞，以及本頁要演的所有麻煩。

      雜湊函式：按姓氏筆畫分信箱

      雜湊函式就是一台「分信機」：任何 key 丟進去，吐出一個 0～m-1 的格子編號。本頁用最簡單的一種——取餘數：h(key) = key % m（key 除以 m，看餘數是多少）。餘數一定落在 0 到 m-1 之間，剛好對應 m 個信箱，一個都不會超出。

      key 是字串怎麼辦？先把它變成數字再取餘數。本頁示範最陽春的做法：把每個字元的內碼加總——"cat" 是 c(99) + a(97) + t(116) = 312，再 312 % 7 = 4，住第 4 格。（這個做法有個大缺點，「常見誤解」那一段會踢爆它。）

      為什麼桶數 m 要挑質數（7、11、17…）？

      現實資料常常「有規律」：都是偶數、都是 10 的倍數、都差固定間隔。如果 m = 8 而 key 是 8、16、24、32——全部 % 8 都等於 0，整批資料擠進同一格，雜湊表直接退化。質數跟絕大多數間隔「無公因數」，規律資料也能被打散。所以本頁用 m = 7，rehash 之後翻倍取質數變 17。

      關鍵 好的雜湊函式只求一件事：把 key 儘量均勻地撒進 m 個格子。撒得越勻，每格越淺，三個 O(1) 才成立。

      先破除一個直覺：「用 key 直接當陣列索引不就好了？」

      如果 key 是 0～99 的小整數，確實可以：開一個 100 格的陣列，a[key] 一步到位——這叫直接定址，它才是真正「永遠 O(1)」的東西。但它馬上撞牆：

      • key 可能很大 —— 身分證字號、手機號碼是 10 位數，你要開一百億格的陣列來存三筆資料嗎？
      • key 可能不是數字 —— 字串 "cat" 沒辦法直接當索引。

      所以只好壓縮：用雜湊函式把「巨大的 key 世界」硬塞進「小小的 m 格」。而只要格子比可能的 key 少——8 隻鴿子飛進 7 個籠子，一定有一籠擠兩隻——碰撞不是意外，是數學上必然發生的宿命（鴿籠原理）。

      關鍵 雜湊表的設計核心從來不是「避免碰撞」（辦不到），而是「碰撞發生時怎麼收拾」。收拾的兩大門派，就是畫面上左右那兩張表。

      關鍵觀察：兩大門派怎麼收拾碰撞

      鏈結法 Chaining（左表）開放定址 Open Addressing（右表）
      哲學不搶位子——同格的人串成一條鏈，往「格子外面」長不掛鏈子——被佔就看下一格，往「表的裡面」擠（線性探測）
      額外記憶體每個節點多一根指標零——全部住在同一個陣列裡，快取友善
      刪除把節點摘掉就好，超簡單陷阱！直接清空會弄斷別人的探測路，要放墓碑 🪦
      表滿了（α > 1）還能塞，只是鏈越來越長塞不下——α 最多到 1，而且 0.7 就開始痛苦
      怕什麼爛雜湊函式讓某條鏈獨長連續佔用「結塊」（primary clustering）：塊越大越容易被撞、撞了塊又更大
      所以 遊戲把兩張表並排、餵同一串資料，就是要讓你親眼看到：同一次碰撞，兩種哲學走出完全不同的後續——尤其查找成本，常常一邊 1 格、另一邊 4 格。

      演算法

      三種操作，兩張表各自的動作：

      1. 插入 key —— 先算 h = key % m。鏈結法：掛到第 h 格鏈條最前面（就算撞了也只是鏈長 +1）。開放定址：第 h 格空的就住下；被佔就看 h+1、h+2……（到尾端繞回 0），遇到的第一個空格或墓碑就是新家。
      2. 查找 key —— 一樣先算 h。鏈結法：只翻第 h 格那條鏈，逐節點比對。開放定址：從第 h 格沿路探測，看到 key 就是找到；看到「從沒住過人的空格」才能說不存在——墓碑不算空格，必須跨過去繼續走。
      3. 刪除 key —— 鏈結法：找到節點、從鏈上摘掉，結束。開放定址：找到之後不能清空，改放墓碑 🪦（標記「這裡曾有人住，查找請繼續往下」）。
      最常漏 開放定址查找的停止條件是「真正的空格」，不是「走過 key 該在的那格」。忘了這件事（或把墓碑當空格），被擠到後面的資料就永遠找不到了。

      刪除陷阱：為什麼非放墓碑不可（反例實演）

      用「刪除陷阱」關卡的資料走一次。10、17、24 全部 % 7 = 3，開放定址下依序住進 3、4、5 格。現在刪掉 17：

      做法刪 17 之後查 24 會發生什麼結果
      直接清空第 4 格 24 % 7 = 3 → 看第 3 格（是 10）→ 看第 4 格（空的！）→ 停 回報「不存在」——但 24 明明就住在第 5 格！
      放墓碑 🪦 看第 3 格（10）→ 第 4 格（墓碑，不能停）→ 第 5 格（24 ✓） 正確找到

      探測路徑就像一串腳印：空格 = 路的盡頭。24 當初是「踩著第 4 格被佔」才被擠去第 5 格的；把第 4 格清空，等於把路從中間挖斷。墓碑的意思是「此路不斷，繼續走」。墓碑會在下次 rehash 時整批清掉；進階實作還會讓插入直接重複利用墓碑的位子（本頁的模擬就是這樣做的）。

      載入因子 α 與 rehash

      α = n ÷ m（資料筆數 ÷ 桶數），白話就是「表有多滿」。它直接決定平均要看幾格：

      • 鏈結法 —— 平均鏈長就是 α，成功查找平均約看 1 + α/2 個節點。α = 2 也只是平均每鏈兩節，慢得很溫和。
      • 開放定址（線性探測） —— 成功查找平均約 (1 + 1/(1−α)) / 2 格。注意分母的 1−α：α = 0.5 時約 1.5 格，α = 0.7 約 2.2 格，α = 0.9 直接 5.5 格——不是慢慢變差，是斷崖式惡化。遊戲側欄的曲線畫的就是這兩條公式。

      所以工程上訂一條警戒線（本頁 0.7；std::unordered_map 預設 1.0）：α 一超標就 rehash——桶數翻倍再取最近的質數（7 → 17），然後每一筆資料用新的 m 重算雜湊值、重新安家。搬一次全家是 O(n)，但因為每次都翻倍，攤平到每次插入平均還是 O(1)——跟動態陣列（vector）翻倍擴容是同一招。

      手算一次：把 10、17、24 塞進 m = 7

      考試在紙上追蹤雜湊表，就是畫這張表。三個 key 除以 7 餘數都是 3——最擁擠的情況：

      步keyh = key % 7鏈結法（第 3 格的鏈）開放定址
      1103[10]第 3 格空 → 住 3
      2173碰撞！[17→10]3 被佔 → 探 4 → 住 4
      3243碰撞！[24→17→10]探 3、4 都被佔 → 住 5
      4查 243鏈第 1 節就是 24 → 看 1 節探 3(10)、4(17)、5(24) → 看 3 格

      同樣的碰撞，兩邊付的代價不一樣——這就是「大塞車」關卡在演的事。

      複雜度

      • 平均 O(1) —— 成立的前提有兩個：雜湊函式撒得夠勻 ＋ α 壓得夠低（靠 rehash 維持）。這時每格平均只有常數筆資料，插查刪都只碰自己那一格附近。
      • 最壞 O(n) —— 全部 key 撞進同一格：鏈結法退化成一條 n 節長鏈，開放定址退化成連續 n 格的大結塊，查一次要翻整張表。爛雜湊函式或惡意構造的輸入就能做到。
      • 空間 O(n + m) —— n 筆資料本體，加上 m 個桶的骨架（包括空桶）。
      • rehash 攤銷 O(1) —— 單次 rehash 搬全家 O(n)，但翻倍策略讓它平均到每次插入只剩常數。

      常見誤解

      • 「雜湊表永遠 O(1)」 —— 錯。O(1) 是平均且有條件的（好雜湊＋低 α）。最壞 O(n)，而且 rehash 那一下是實打實的 O(n)。對延遲敏感的系統（遊戲引擎、交易系統）會特別提防這兩點。
      • 「發生碰撞代表雜湊函式寫爛了」 —— 錯。只要格子比 key 的可能值少，碰撞就必然存在；好函式只是讓碰撞「均勻地少」，不是零。
      • 「開放定址刪除＝把那格清空」 —— 錯，這是本頁演過的反例：清空會弄斷後面所有人的探測路，明明存在的 key 會被回報不存在。要放墓碑。
      • 「字串雜湊用字元加總就好」 —— 差勁。"cat" 和 "act" 字元相同、只是順序不同，加總完全一樣 → 保證碰撞（「字串信箱」關卡演的就是這個）。實務用多項式雜湊：h = h·31 + c，讓「順序」也參與運算。
      • 「α 到 1 之前都沒事」 —— 對鏈結法勉強成立，對開放定址大錯：0.7 之後平均探測次數沿著 1/(1−α) 起飛，側欄那條橘色曲線就是證據。

      開放定址版程式（右表跑的就是這個）

      三種格子狀態是關鍵：空（從沒人住）、有人、墓碑（住過但被刪了）：

      struct OpenAddr {
    enum State { EMPTY, USED, TOMB };            // 空 / 有人 / 墓碑
    vector<int>   key;
    vector<State> st;
    OpenAddr(int m = 7) : key(m), st(m, EMPTY) {}
    int m() const { return (int)key.size(); }

    void insert(int k) {
        int i = k % m();
        while (st[i] == USED) i = (i + 1) % m(); // 被佔就往下一格（墓碑可直接重用）
        key[i] = k; st[i] = USED;
    }
    bool find(int k) const {
        int i = k % m();
        while (st[i] != EMPTY) {                 // 墓碑不能停，只有真空格能停！
            if (st[i] == USED && key[i] == k) return true;
            i = (i + 1) % m();
        }
        return false;
    }
    void erase(int k) {
        int i = k % m();
        while (st[i] != EMPTY) {
            if (st[i] == USED && key[i] == k) { st[i] = TOMB; return; }  // 放墓碑
            i = (i + 1) % m();
        }
    }
};

      整體設計：先算完，再播放

      使用者按「下一步」之前，整段過程已經全部算好了。特別的是這一關一份輸入要同時餵兩個模擬器——鏈結法和開放定址在 buildSteps 裡肩並肩往前走，每一步都把兩張表各拍一張快照。

      操作序列 +10 +17 ?17 -10 !
      buildSteps(ops) 兩個模擬器同步跑完整串操作
      steps[] 每一格 = 兩張表當下的完整快照
      畫面只負責把 steps[目前步數] 畫出來

      為什麼這樣設計

      • 前進後退變成加減一 —— 「倒退一次線性探測」或「還原一次 rehash」的反向邏輯根本不用寫。
      • 兩張表天然同步 —— 同一個 step 物件裡同時有 chain 和 open 兩份快照，左右畫面永遠對得上，不會一邊快一邊慢。
      • 演算法與畫面分離 —— buildSteps 裡沒有半行畫面程式碼，它就是純粹的雜湊表模擬器。
      代價 每步存兩張表的完整快照，記憶體 O(步數 × m)。教學規模（十幾個操作、m ≤ 17）毫無問題，真實工程不會這樣寫。
