呼叫堆疊

遞迴不是魔法。每呼叫一次函式，電腦就幫你推入一個框架（frame）；每 return 一次就彈出一個。你一直都在用堆疊 —— 只是這個堆疊由系統替你管理，看不見而已。這一頁把它畫出來。

01

怎麼玩・你會學到什麼

三個範例，堆疊長相完全不同。

怎麼玩

  1. 選一個範例：階乘（堆疊像一條直線）、費氏數列（呼叫次數爆炸）、河內塔（兩次遞迴夾一個動作）。
  2. 拉滑桿選 n，數字不用大 —— 費氏設到 8 就很有感覺了。
  3. 按 下一步，看每一次呼叫怎麼 PUSH 一個新框架、每一次 return 怎麼 POP 掉它。
  4. 每個框架上都寫著它現在卡在哪——「要等下面算完才能繼續」。
  5. 看不懂就 上一步 倒回去。這一頁特別值得反覆倒帶。
盯這兩個數字 右下角的 總呼叫次數 和 最大深度。切到費氏模式，你會看到呼叫次數衝到幾十次，但最大深度始終只有 n。這個差距是整頁最重要的觀念。

你會學到什麼

  • 遞迴到底怎麼被執行 —— fact(5) 呼叫 fact(4) 時，原本的 n=5 跑去哪了？為什麼沒被蓋掉？
  • 一個 frame 裡裝什麼 —— 參數、區域變數、回傳位址。第三個才是關鍵。
  • 遞迴的三個要素 —— 基底條件、遞迴關係、收斂性。少一個就爆。
  • 呼叫次數 ≠ 堆疊深度 —— fib(30) 呼叫 270 萬次，但堆疊只有 30 層深。所以它是「慢」不是「爆」。
  • Stack Overflow 怎麼發生的 —— 為什麼遞迴太深會炸，但迴圈跑一億次不會。
  • 河內塔的三步法 —— 以及 2ⁿ−1 這個最少步數怎麼推出來。
  • 遞迴改迭代 = 自己接管那個堆疊 —— 為什麼 push 的順序要反過來寫。
建議順序 階乘 n=4（看清 push/pop 節奏）→ 費氏 n=6（看呼叫次數爆炸、深度卻不變）→ 河內塔 n=3（看兩次遞迴中間夾一個動作）。

這個遊戲跑的程式（完整版）

上面每一次 PUSH／POP，就是這三個函式的某一行在執行。注意每個函式的第一行都是基底條件 —— 階乘在 n ≤ 1 時直接回傳 1、費氏在 n ＜ 2 時直接回傳 n、河內塔在 n = 0 時什麼都不做。遊戲裡指標走到「基底條件」那一步，對應的就是這一行；少了它就是無限 push，直到 Stack Overflow。

// 階乘：一條直線的遞迴
long long fact(int n) {
    if (n <= 1) return 1;              // 基底條件 —— 沒有它就 stack overflow
    return n * fact(n - 1);            // 等下面算完，我才能乘
}

// 費氏：一次呼叫兩次 → 呼叫次數爆炸
long long fib(int n) {
    if (n < 2) return n;               // 基底條件
    return fib(n - 1) + fib(n - 2);    // fib(n-1) 完全跑完並 pop 掉，才輪到 fib(n-2)
}

// 河內塔：兩次遞迴中間夾一個動作
void hanoi(int n, char a, char c, char b) {   // 把 n 個盤子從 a 移到 c，b 當中繼
    if (n == 0) return;                // 基底條件：沒有盤子要搬
    hanoi(n - 1, a, b, c);             // 上面 n-1 個先搬去中繼柱
    printf("盤子 %d: %c → %c\n", n, a, c);
    hanoi(n - 1, b, c, a);             // 中繼柱那疊再搬回來蓋上
}
03

這個功能是怎麼做到的

大部分人會寫遞迴，但講不出下面這三件事。

核心問題：遞迴到底是怎麼被執行的

  • fact(5) 呼叫 fact(4) 時，原本的 n=5 跑去哪裡了？為什麼沒有被蓋掉？
  • fact(1) 回傳之後，電腦怎麼知道要跳回哪一行繼續執行？
  • 為什麼遞迴太深會 Stack Overflow，但迴圈跑一億次卻不會？

答案全都是同一個東西：呼叫堆疊。

一個 frame 裡到底裝了什麼

┌──────────────────────────────────┐
│  fact(3)   ← 一個 Stack Frame     │
├──────────────────────────────────┤
│  參數：n = 3                      │  ← 每一層都有自己的 n，互不干擾
│  區域變數：（這題沒有）            │
│  回傳位址：回到 fact(4) 的第 5 行  │  ← 最關鍵！算完要知道回哪裡
└──────────────────────────────────┘
兩個答案 為什麼每層的 n 不會互相蓋掉？因為 n 存在各自的 frame 裡，根本不是同一個變數。
為什麼算完知道要回哪？因為 frame 裡存了回傳位址。
而後呼叫的函式一定先結束 —— 完美的 LIFO，所以用堆疊。

呼叫時（push）

  • 配置一塊新 frame
  • 把參數複製進去
  • 記下「回來時要跳到哪一行」
  • 堆疊指標往上移

return 時（pop）

  • 把回傳值交給下面那層
  • 整塊 frame 直接丟棄（區域變數瞬間消失）
  • 跳回記下的那一行繼續執行
  • 堆疊指標往下移

遞迴的三個要素，缺一個就爆

  1. 基底條件：什麼時候可以不用再遞迴，直接給答案。
    缺了它 → 無限 push → Stack Overflow。
  2. 遞迴關係：把大問題拆成同樣形狀但更小的問題。
    fact(n) 交給 fact(n−1)、hanoi(n) 交給兩個 hanoi(n−1)。
  3. 收斂性：每呼叫一次都必須更靠近基底。
    寫成 fact(n) 呼叫 fact(n) 就永遠到不了基底。
Stack Overflow 堆疊的大小是固定的（CPython 預設遞迴上限 1000 層，C 的執行緒堆疊常見 1 MB）。忘了寫基底條件 → 一直 push 卻永遠不 pop → RecursionError 或 Segmentation fault。
所以寫遞迴的第一件事永遠是：先寫終止條件，再寫遞迴呼叫。

★ = 一模一樣的子問題被重算了一次
子問題fib(4)fib(3)fib(2)fib(1)fib(0)總呼叫
被呼叫幾次112329

呼叫次數公式是 2·F(n+1) − 1：n=4 時 9 次、n=10 時 177 次、n=30 時 270 萬次、n=50 要跑好幾年。

慢的原因不是遞迴本身，而是重複計算 —— 同一個 fib(2) 被算了很多次。加上 memo（開一個陣列或 unordered_map）記住算過的結果，呼叫次數立刻降到 2n−1，時間從 O(2ⁿ) 變 O(n)。

本頁最重要的一句話：呼叫次數 ≠ 堆疊深度

關鍵 fib(30) 呼叫 270 萬次，但堆疊最深只有 30 層。

因為 fib(n-1) 這棵子樹會整個跑完並被彈光，fib(n-2) 才開始 —— 兩邊不會同時存在於堆疊上。

所以 fib 的問題是時間爆炸（O(2ⁿ)），不是記憶體爆炸（空間只有 O(n)）。很多人誤以為 fib(30) 會 Stack Overflow —— 它不會，它只是慢。

把上面的遊戲切到費氏模式，盯著「總呼叫次數」和「最大深度」兩個數字，親眼看它們拉開差距。

河內塔：三步法

三根柱子 A、B、C，n 個大小不同的盤子一開始由大到小疊在 A 上。把它們全部搬到 C，規則：

  1. 一次只能搬一個盤子。
  2. 只能搬每根柱子最上面的盤子。（這句話就是在說「柱子是堆疊」）
  3. 任何時候都不能把大盤子壓在小盤子上面。

不要試著去想「第一步該搬哪個盤子」，那會直接卡死。假設 hanoi(n−1) 已經有人幫你做好了，那 n 個盤子的解法必然是這三步：

  1. 把上面 n−1 個從 A 搬到中繼柱 B（借 C 當中繼）→ hanoi(n−1, A, B, C)
  2. 把最大的第 n 個從 A 直接搬到 C → 一步，就是印出來的那一行
  3. 把 B 上的 n−1 個搬到 C（借 A 當中繼）→ hanoi(n−1, B, C, A)
兩個為什麼 為什麼一定合法？第 2 步搬的是最大的盤子，此時 C 是空的，A 上除了它也沒別的 —— 不可能違反「大不能壓小」。
為什麼可以假設 n−1 個已經會搬？這就是數學歸納法，也是遞迴的本質：你只負責定義「這一層怎麼拆」，剩下的交給更小的自己。

河內塔的最少步數怎麼推

# 三步法裡只有第 2 步真的搬盤子
T(n) = 2·T(n-1) + 1       # 兩次 n-1 的搬移，加上中間那一步
T(0) = 0

# 展開：
T(n) = 2·T(n-1) + 1
     = 4·T(n-2) + 2 + 1
     = 8·T(n-3) + 4 + 2 + 1
     = 2^k·T(n-k) + (2^k - 1)
     = 2^n·T(0) + 2^n - 1  =  2^n - 1   # 令 k = n

所以 n=3 是 7 步、n=10 是 1023 步。傳說中的 64 個金盤需要 2⁶⁴−1 ≈ 1.8×10¹⁹ 步，就算一秒搬一個也要 5850 億年。

注意呼叫次數（2ⁿ⁺¹−1）比搬移次數（2ⁿ−1）多，因為 hanoi(0) 那些「什麼都不做就 return」的空呼叫也各佔一個 frame。在遊戲裡對照這兩個數字看得很清楚。

遞迴改迭代，其實是「自己接管那個堆疊」

// 遞迴版：電腦幫你管理堆疊
void hanoi(int n, char a, char c, char b) {
    if (n == 0) return;
    hanoi(n-1, a, b, c);  move(n, a, c);  hanoi(n-1, b, c, a);
}

// 迭代版：你自己拿一個 stack 當堆疊，把「還沒做的任務」推進去
struct Task { int n; char a, c, b; bool expanded; };   // expanded = 是否已展開

void hanoiIter(int n, char a, char c, char b) {
    stack<Task> st;
    st.push({n, a, c, b, false});        // false = 這個任務還沒展開
    while (!st.empty()) {
        Task t = st.top(); st.pop();
        if (t.n == 0) continue;
        if (t.expanded) {
            move(t.n, t.a, t.c);         // 已展開過 → 執行中間那一步
        } else {
            st.push({t.n - 1, t.b, t.c, t.a, false});   // 注意：順序要反過來 push
            st.push({t.n,     t.a, t.c, t.b, true});    // 因為堆疊是後進先出
            st.push({t.n - 1, t.a, t.b, t.c, false});
        }
    }
}

兩版做的事完全一樣，差別只在堆疊由誰管理。

  • 自己管理的好處 —— 不受遞迴深度上限限制、可以隨時暫停／存檔／繼續、除錯時能直接印出整個堆疊。
  • 代價 —— 程式碼變醜，而且 push 的順序必須反過來寫（因為 LIFO）。這一點最容易寫錯。

這也解釋了 07 迷宮 那一頁為什麼 DFS 可以寫成迴圈：它就是自己拿一個陣列當呼叫堆疊。

五個最常見的錯誤

  • 忘記基底條件 —— 一路 push 到堆疊耗盡：C/C++ 直接 Segmentation fault，Python 則丟 RecursionError。
  • 參數沒有變小 —— 寫成 fact(n) 呼叫 fact(n)，或 fib(n-1) 打成 fib(n)。
  • 以為每層共用同一個 n —— 其實每個 frame 各有一份，改了不會互相影響。
  • 把呼叫次數當成堆疊深度 —— 誤以為 fib(30) 會 Stack Overflow。它只是慢，不會爆。
  • 迭代版 push 順序沒反過來 —— 河內塔的步驟順序整個顛倒。
04

程式架構與說明

這一頁的做法有個很有意思的地方 —— 它用真的遞迴去演示遞迴。

整體設計：用真遞迴錄影，再回放

要畫出呼叫堆疊，最誠實的方法就是真的去跑一次遞迴，一邊跑一邊錄下每個事件。本頁分成兩層：

選模式與 n
真的執行一次遞迴 fact / fib / hanoi 就寫在裡面
事件串 call / status / move / ret
把事件重播成快照 維護一份自己的 frames 陣列
steps[] → render() 畫出來
有趣的地方 錄影階段用的是語言真正的呼叫堆疊（JavaScript 自己的），重播階段則是我們手動維護的一個陣列。同一件事被做了兩次 —— 一次是隱形的，一次是畫得出來的。這正好就是第 03 段講的「遞迴 vs 自己管理堆疊」。

四種事件

事件什麼時候發出重播時做什麼
call進入函式的第一行push 一個 frame，呼叫次數 +1，更新最大深度
status函式卡住、要等子呼叫時改寫頂端 frame 的說明文字（「我在等什麼」）
move河內塔真的搬一片盤子時在右邊的紀錄追加一行
ret函式 return 前把頂端標成 dying、拍一張快照，然後 pop
順序細節 ret 事件是先拍快照才 pop。這樣畫面上才看得到「這個 frame 正在死掉」的那一格，而不是它憑空消失。教學動畫的關鍵常常就在這種一行的順序。

一個 step 長什麼樣

{
  frames:   // 那一刻整個呼叫堆疊的快照（每格有 fn 和 st）
  out:      // 右邊紀錄的快照
  depth:    // 目前深度
  maxDepth: // 到目前為止的最大深度
  calls:    // 累計呼叫次數  ← 和 maxDepth 對照，就是本頁的重點
  flag:     // 'push' / 'pop' / 'move' → 決定徽章和高亮
  msg, cls: // 說明面板
}

calls 和 maxDepth 被刻意放在同一個快照裡，就是為了讓畫面能同時顯示這兩個數字。整頁最重要的觀念，靠的是兩個欄位的並排。

畫面：frame 的四種狀態

狀態顏色意思
newborn綠色這一步剛被 push 進來
top深橘CPU 正在執行的那一層
dying紅色正在 return，下一步就消失
（一般）淺橘卡住了，在等上面那層算完

每個 frame 還會依深度往右縮排一點，堆起來就是一道階梯 —— 一眼看得出遞迴有多深。

你可以怎麼改

想做的事改哪裡
放寬 n 的上限CFG 裡各模式的 max。費氏設太大步驟數會爆炸，慎用
加第四個範例（例如二元樹走訪）在 buildSteps() 加一個分支，照樣發出四種事件即可；畫面完全不用改
加上 memo 版費氏做對照複製 fib 那段，加一個 memo 物件，命中時發出一個新的 hit 事件
顯示「回傳位址」欄位在 call 事件多帶一個欄位，frame 多印一行

自己動手：給 AI 的 Prompt

用 C++ 幫我把「呼叫堆疊」變成看得見的東西。

寫一個 Tracer 類別：建構時印「進入」、解構時印「離開」，
套在任何遞迴函式的第一行就能印出完整呼叫過程：

long long fact(int n) {
    Tracer t("fact", n);
    if (n <= 1) return t.ret(1);
    return t.ret(n * fact(n - 1));
}

輸出要長這樣（用縮排表示 stack 深度）：
→ fact(5)
  → fact(4)
    → fact(3)
      → fact(2)
        → fact(1)
        ← fact(1) 回傳 1
      ← fact(2) 回傳 2
    ← fact(3) 回傳 6
  ← fact(4) 回傳 24
← fact(5) 回傳 120

要求：
1. 用一個全域變數記錄目前深度：進入 +1、離開 −1，縮排 = 深度 × 2 格
2. 同時統計「總呼叫次數」和「最大深度」，程式結束前印出來
3. 套到 fib(10) 上，數數看呼叫了幾次
4. 查你的環境的執行緒堆疊大小（常見 1–8 MB），
   實測 fact 大約遞迴到幾層會 Segmentation fault

寫完後回答：為什麼 fib(10) 的「呼叫次數」遠大於「最大深度」？

延伸題：遞迴 → 迭代（自己管理堆疊）

把下面三個遞迴改寫成「用 std::stack 當呼叫堆疊」的迭代版，不准用 recursion：

1. fact(n)        —— 最簡單，其實用迴圈就好，但請用 stack 寫一次
2. hanoi(n,a,c,b) —— 提示：stack 裡放「還沒展開的任務」struct Task {n,a,c,b,expanded}
3. 二元樹的中序走訪 inorder(root)

三題都要：
- 印出你的 stack 在每一步的內容
- 驗證輸出和遞迴版完全相同
- 比較兩版的執行時間

最後回答：
- 什麼情況下「自己管理 stack」比遞迴好？（提示：深度、除錯、暫停續跑）
- 什麼是尾遞迴（tail recursion）？g++ -O2 會把哪一種遞迴優化成迴圈？怎麼驗證？

   （你會看到 fib(2) 被算了非常多次）
