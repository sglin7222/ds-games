油漆桶填充

小畫家的油漆桶、踩地雷點到空白格自動翻開一大片、消消樂找出相連的同色方塊 —— 全都是同一個演算法。點一下，看顏色怎麼從那一格一圈一圈漫出去。

01

怎麼玩・你會學到什麼

這一關幾乎不用教怎麼玩 —— 你早就用過一百次了。

怎麼玩

  1. 從色盤挑一個顏色。
  2. 用油漆桶點畫布上任何一個封閉區塊 —— 顏色會擴散開來。
  3. 把速度調慢一點，看清楚擴散的形狀。
  4. 切到 Stack → 蛇形爬行，點另一個區塊，比較兩種擴散形狀。
  5. 用畫筆自己畫圖案，或按換一張圖拿新的圖來玩。
重點觀察 兩種容器的最終結果完全一樣，一格不差 —— 只有過程長得不同。佇列像水波同心圓往外散，堆疊像蛇沿著一條線亂鑽。
一定要試 勾選 8 方向（含斜角） 再填一次。你會看到顏色從斜角的縫隙漏出去，整張圖被灌爆 —— 這就是為什麼所有繪圖軟體的油漆桶都只走 4 方向。

你會學到什麼

  • Flood Fill 就是沒有終點的 BFS —— 迷宮 BFS 是「找到終點就停」，這裡是「走遍整個連通區」。
  • 「上色」本身就是「標記已走訪」 —— 這一題漂亮在不需要額外的 seen 集合，格子改了顏色就不會再被選中。
  • 兩個經典 bug —— 忘記檢查「新舊同色」會無限迴圈；在取出時才上色會重複入列。兩個都會考。
  • 連通性的定義會改變答案 —— 4 方向和 8 方向是兩種不同的「相連」，結果差很多。
  • 原地修改（in-place）的取捨 —— 省了記憶體，但把原圖弄壞了。
  • 一招通吃 —— 島嶼數量、踩地雷、爛橘子、魔術棒，全是這一招換個殼。
建議順序 先用最慢的速度填一個大區塊，看清楚波紋。再切 Stack 填另一塊，看蛇形。最後才勾 8 方向 —— 那個「漏出去」的瞬間最有記憶點。

演算法

O(R×C)

    這個遊戲跑的程式（完整版）

    你點下油漆桶的那一刻，跑的就是這一段。兩行加粗的就是第 03 段要講的兩個關鍵：

    #include <deque>
#include <vector>
using namespace std;

void floodFill(vector<vector<int>>& image, int sr, int sc, int newColor) {
    int oldColor = image[sr][sc];
    if (oldColor == newColor) return;   // 基底防護：沒有這一行會無限迴圈

    int R = image.size(), C = image[0].size();
    deque<pair<int,int>> frontier = {{sr, sc}};
    image[sr][sc] = newColor;           // 起點先上色
    int dr[] = {-1, 1, 0, 0}, dc[] = {0, 0, -1, 1};

    while (!frontier.empty()) {         // frontier 空了 = 整個連通區走完，自然結束
        auto [r, c] = frontier.front(); frontier.pop_front();
        // ↑ 改成 back() + pop_back() → 蛇形爬行，結果一模一樣
        for (int i = 0; i < 4; i++) {
            int nr = r + dr[i], nc = c + dc[i];
            if (nr < 0 || nr >= R || nc < 0 || nc >= C) continue;
            if (image[nr][nc] == oldColor) {
                image[nr][nc] = newColor;    // 放進去的當下就上色
                frontier.push_back({nr, nc});
            }
        }
    }
}
    03

    這個功能是怎麼做到的

    跟 07 的迷宮是同一個模板，但少了一樣東西、多了一個陷阱。

    問題定義

    給一張圖（二維陣列，每格是一個顏色）、一個起點座標、一個新顏色。把所有和起點相連、而且和起點同色的格子換成新顏色。

    「相連」的定義是關鍵：預設指的是上下左右四個方向能一路走過去，不能走斜角。

    它就是 07 的迷宮 BFS，但少了終點

    比較迷宮 BFS（07）油漆桶（本頁）
    什麼時候停碰到終點就停容器空了才停（沒有終點）
    能不能走不是牆就能走顏色等於起始色才能走
    要不要 seen要，額外一個集合不用 —— 上色本身就是標記
    要不要 parent要，才畫得出路徑不用，不關心路徑
    想知道什麼最短路徑整個連通區域
    最漂亮的一點 這一題不需要 seen 集合。因為只要把一格上了新顏色，它就不再等於「起始顏色」了，下次再檢查到它自然會被判定為「不能走」。資料本身就是標記 —— 這在演算法設計裡叫原地標記，能省下一整個資料結構。

    演算法

#include <vector>
using namespace std;

            }
        }
    }
}

    兩個一定要知道的 bug

    Bug 1：忘記檢查「新舊顏色相同」

    如果新顏色和起始顏色一樣，那「把格子改成新顏色」等於什麼都沒做 —— 它永遠還是等於 oldColor。於是同一格會被反覆判定為可走、反覆塞進容器，容器越長越大，直到記憶體爆掉。

    症狀 程式卡住、越跑越慢、最後崩潰。而且只有在「用同色填同色」時才會發生，隨手測試很容易漏掉。在上面的遊戲用同色點同一區，會看到提示直接 return。

    Bug 2：在取出時才上色，而不是放進去時

    假設格子 X 的左邊和上面都是同色。左邊那格處理時把 X 放進容器一次，上面那格處理時又把 X 放進去一次 —— 因為 X 這時候還沒被上色。

    寫法結果正確嗎容器大小速度
    放進去時上色（對）正確每格最多進去一次快
    取出時才上色（錯）仍然正確可能膨脹好幾倍慢好幾倍

    注意這個 bug 不會讓答案錯，只會讓程式變慢 —— 所以它更難被發現。這也是 07 迷宮那一頁講的同一件事：標記要在入列的當下做。

    4 方向與 8 方向：連通性的定義

    「相連」不是一個絕對的概念，是你自己定義的。改變定義，答案就變。

    • 4 方向連通 —— 上下左右。兩格必須有一整條邊貼在一起才算相連。
    • 8 方向連通 —— 再加上四個斜角。兩格只要碰到一個角就算相連。

    用畫筆畫的斜線在 4 方向下是一道密不透風的牆，但在 8 方向下每個轉折處都有一個角可以鑽過去 —— 所以顏色會漏出去。

    所以 繪圖軟體的油漆桶一律用 4 方向，因為使用者畫的線條在直覺上就是密封的。但在影像處理找連通區域時常常用 8 方向，因為斜著相鄰的像素通常屬於同一個物體。沒有哪一個比較對，看你要什麼。

    複雜度

    • 時間 O(R × C) —— 每一格最多被上色一次、被取出一次。即使圖很大也只掃一遍。
    • 空間 O(R × C) —— 最壞情況（整張圖同色）容器會裝下大半張圖。
    • 和用佇列還是堆疊無關 —— 兩者都是 O(R × C)，差別只在容器裡同時堆著多少東西的形狀。

    同一招，你早就用過很多次

    應用怎麼用到 Flood Fill
    小畫家油漆桶就是本體。點一下，同色區域全部換色
    踩地雷點到空白格時，自動翻開整片相連的空白區
    Photoshop 魔術棒Flood Fill 加上顏色容差（相近的顏色也算同一區）
    消消樂 / 泡泡龍找出所有相連的同色方塊，一起消除
    島嶼數量（LeetCode 200）每次填掉一整塊陸地，填了幾次就是幾座島
    影像處理連通區域標記（Connected Component Labeling）

    常見誤解

    • 「用 Queue 和用 Stack 結果會不一樣」 —— 一樣，一格不差。因為最後整個連通區都會被走遍，順序不影響集合。順序只影響過程的樣子和容器的最大長度。
    • 「一定要用遞迴寫」 —— 不用。遞迴版寫起來短，但大圖會爆堆疊（stack overflow）。用明確的容器寫成迴圈就沒有這個問題。
    • 「要先算出區域有多大再填」 —— 不用。邊走邊填就好，這正是這個演算法簡潔的地方。
    • 「原地修改比較好」 —— 省記憶體，但破壞了原圖。如果之後還要用原圖，就得先複製一份，或者改用獨立的 seen 集合。
    04

    程式架構與說明

    只講流程與分工，不逐行拆解。

    整體設計：邊算邊播，而且是局部更新

    畫布有 640 格，如果每動一格就把整張畫布重畫一次，會非常卡。所以這一頁跟前幾頁的做法不同：

    頁面畫面更新方式為什麼
    01 括號先算完，整批重畫格子少，而且要能倒退
    06 約瑟夫邊算邊播，整批重畫最多 24 人，重畫成本可忽略
    08 油漆桶（本頁）邊算邊播，只改動到的那一格640 格，整批重畫會掉幀
    取捨 局部更新快，但要自己確保「資料改了、畫面也一定跟著改」。本頁的做法是把兩件事綁進同一個函式 setPixel() —— 只要不繞過它，就不可能漏改。

    模組分工

    層主要函式負責什麼
    畫布buildCanvas
    setPixel    		建立 640 個格子；setPixel 是唯一能改顏色的入口，同時改資料和畫面。
    圖案line / rect / circle
    drawShapes / drawHouse…    		用最基本的畫線函式組出預設圖案。跟演算法完全無關。
    演算法startFill
    fillStep    		核心。startFill 做初始化與那個關鍵檢查，fillStep 每次處理一批格子。
    控制stopFill / setAlgo
    setMode    		播放、演算法切換、工具切換。

    核心：startFill() 與 fillStep()

    點擊某一格 (r, c)
    起始色 == 新色？是 → 直接 return，避免無限迴圈
    frontier ← [起點]，起點上色
    計時器反覆呼叫 fillStep()
    取出一格useQueue ? shift() : pop()
    鄰居 == 起始色？上色 + 放進 frontier
    frontier 空了停止

    速度拉到很快時，fillStep() 一次會處理 4 到 12 格（批次處理），否則畫面更新的速度會跟不上計時器。這是純粹的顯示技巧，跟演算法無關。

    一個小地方：d 欄位在做什麼

    放進容器的每一格除了座標之外還帶了一個 d（層數），就是「離起點幾步」。演算法本身完全不需要它，純粹是為了在畫面上顯示「目前層數」。

    但它不是沒用的東西 —— 只要把這個層數留下來，這支程式就變成了「爛橘子」那一題（幾分鐘後全部腐爛 = 最大層數）。多存一個欄位，就多解一題。

    自己動手：給 AI 的 Prompt

    用 C++ 的 std::deque 實作 Flood Fill（油漆桶）。

函式：floodFill(image, sr, sc, newColor)
- image 是二維陣列，每格是一個顏色值
- (sr, sc) 是點擊位置
- 把所有和 (sr, sc) 相連且同色的格子換成 newColor

要求：
1. 用 std::deque
2. 只走上下左右 4 個方向
3. 處理 oldColor == newColor 的情況（否則會無限迴圈）
4. 在放進容器時就上色，不要等取出來才上色 —— 說明為什麼

測資：
image = [[1,1,1],
         [1,1,0],
         [1,0,1]]
floodFill(image, 1, 1, 2)
應該得到 [[2,2,2],
          [2,2,0],
          [2,0,1]]
