括號堆疊闖關

01

怎麼玩・你會學到什麼

先看這一段，再往下玩。

怎麼玩

畫面上有一條字串和一座堆疊塔。指標從最左邊往右走，每走一格，堆疊就會有反應。

演示模式

  1. 從上方挑一個關卡，或自己輸入一串括號。
  2. 按 下一步 一格一格走；也可以按 自動播放 讓它自己跑。
  3. 邊走邊看四件事同步變化：字元顏色、下方配對弧線、右邊堆疊塔、演算法高亮行。
  4. 隨時可以 上一步 倒回去，看不懂的地方反覆走。

闖關模式

  1. 每碰到一個括號，先不告訴你答案，由你選：推入、彈出、還是判定失敗。
  2. 答對得分，連續答對會有額外加分；答錯會立刻說明正確答案和理由。
  3. 一關結束會結算正確率，可以直接跳下一關。
操作 鍵盤 → 下一步、← 上一步、空白鍵 播放／暫停。

你會學到什麼

  • 堆疊的 LIFO 特性 —— 後進先出。為什麼「後開的括號要先關」剛好就是這個規則。
  • push 與 pop 兩個動作 —— 什麼時候該推入、什麼時候該彈出，以及為什麼只需要看頂端。
  • 為什麼不能只用計數器 —— 這是本頁最重要的一個觀念，第 03 段會用 ([)] 這個反例打破它。
  • 三種失敗情形的完整分類 —— 右括號太多、種類不符、左括號沒關完。少判一種就是錯的程式。
  • 複雜度分析 —— 為什麼掃一遍就夠，時間是 O(n)。
  • 把演算法讀成畫面 —— 程式碼跑到第幾行，畫面就在做什麼，兩者對起來看。
建議順序 先用演示模式走完 (()) 和 {[()]} 建立直覺，再切闖關模式從 ([)] 開始。那一關幾乎所有人第一次都會答錯。

      歷程

      1. 還沒開始。

      這個遊戲跑的程式（完整版）

      把教學用的視覺化全部拿掉，這個演算法本體就是這樣——第 03 段講的東西，一行不多一行不少：

      #include <stack>
#include <string>
using namespace std;

bool isBalanced(const string& s) {
    stack<char> st;
    for (char c : s) {
        if (c == '(' || c == '[' || c == '{') {
            st.push(c);                               // 左括號 → 推入
        } else if (c == ')' || c == ']' || c == '}') {
            if (st.empty()) return false;             // 失敗①：右括號太多
            char open = (c == ')') ? '(' : (c == ']') ? '[' : '{';
            if (st.top() != open) return false;       // 失敗②：種類不符
            st.pop();                                 // 配對成功，這一對結案
        }
        // 其他字元：什麼都不做
    }
    return st.empty();                                // 失敗③：左括號沒關完
}

      十行左右。遊戲頁面多出來的幾百行，全部都是為了「讓過程看得見」——這是教學程式和生產程式的差別。

      03

      這個功能是怎麼做到的

      從問題定義走到完整演算法，中間每一個判斷為什麼非要不可。

      問題定義

      給一個字串，裡面可能有 ( ) [ ] { } 六種括號和其他任意字元。判斷所有括號是否「完全匹配」——每個左括號都有對應的右括號、種類相同、而且不能交錯。

      字串結果原因
      (())合法內層先關，外層後關
      ()[]{}合法三對各自獨立，互不影響
      ([)]不合法交錯了。[ 比 ( 晚開，卻比它晚關
      (()不合法有一個 ( 到最後都沒關
      ())(不合法第 2 格的 ) 沒有對象

      先破除一個直覺：用數的不行

      很多人第一個想法是「左括號數 = 右括號數就好」。這個想法會在兩個地方壞掉。

      • 順序沒管到 —— )( 左右各一個，數量相等，但顯然不合法。補救辦法是「掃描過程中計數不能變成負的」。
      • 種類沒管到 —— ([)] 每種括號都恰好一左一右，計數從頭到尾也沒有變負，但它就是不合法。不管怎麼加強計數器都救不了這一個。
      關鍵 計數器只記得「還有幾個沒關」，記不得「還沒關的是誰、以什麼順序排隊」。而 ([)] 的錯誤，恰恰就藏在這個順序裡。

      關鍵觀察：後開的一定先關

      把合法字串攤開來看，會發現一條鐵律：任何時候遇到右括號，它要配的一定是「目前還沒關的左括號裡，最晚出現的那一個」。

      以 {[()]} 走到第 3 格的 ) 為例，此時還沒關的有 {、[、(。這個 ) 不可能去配 { 或 [——如果它跳過 ( 去配別人，( 就永遠被關在外面出不來了。所以它只能配最晚出現的 (。

      所以 「最晚進來的最先出去」就是 後進先出（LIFO），而後進先出正是堆疊的定義。所以這題用堆疊不是巧合，是問題結構本身逼出來的。

      演算法

      準備一個空堆疊，由左往右掃過字串。每個字元只有三種可能：

      1. 是左括號 —— 推入堆疊（push）。意思是「這個還在等它的另一半，先記著」。
      2. 是右括號 —— 只跟堆疊頂端比對。
        頂端如果是同種左括號 → 彈出（pop），這一對結案。
        堆疊如果是空的、或頂端種類不對 → 立刻失敗，不用再掃下去。
      3. 不是括號 —— 直接略過，堆疊不動。

      掃完之後還要做最後一次檢查：堆疊必須是空的。如果還有東西，代表那些左括號到最後都沒被關掉。

      最常漏 迴圈結束後那一行 「堆疊必須為空」 是初學者最常忘記寫的。忘了它，((( 會被判成合法。

      三種失敗，缺一不可

      失敗種類發生時機例子白話
      堆疊已空遇到右括號，但堆疊沒東西())(右括號太多了
      種類不符頂端的左括號跟這個右括號不是同一種([)]括號交錯了
      剩餘未關字串掃完了，堆疊還有東西(()左括號沒關完

      前兩種在迴圈裡發現，第三種在迴圈結束後發現。三種都要判，程式才是對的。

      手算一次：{[()]}

      考試要你在紙上追蹤時，就是畫這張表。堆疊由左到右代表由底到頂。

      步i字元動作堆疊（底→頂）
      0——建立空堆疊（空）
      10{push{
      21[push{ [
      32(push{ [ (
      43)頂端是 ( → pop{ [
      54]頂端是 [ → pop{
      65}頂端是 { → pop（空）
      7——掃完，檢查堆疊空 → 成功

      注意堆疊的高度變化：先一路長到 3，再一路降回 0。這個「先上後下」的形狀，就是巢狀結構在堆疊上的樣子——也就是遊戲畫面裡弧線越畫越高、又收回來的原因。

      複雜度

      • 時間 O(n) —— 每個字元只被看一次，每次做的事（push、pop、比對）都是固定成本。
      • 空間 O(n) —— 最壞情況是 ((((… 全部是左括號，堆疊會長到跟字串一樣高。
      • 不需要回頭 —— 這是堆疊解法最漂亮的地方：指標永遠往前，從不倒退，一遍就掃完。

      常見誤解

      • 「遇到右括號就去堆疊裡找有沒有同種的」 —— 錯。只能看頂端。往下找等於允許交錯，([)] 會被誤判成合法。
      • 「先掃一遍算數量，再掃一遍檢查」 —— 沒必要，也不夠。一遍就能做完，而且數量對了也不代表合法。
      • 「發現錯誤還要繼續掃完」 —— 不用。三種失敗只要碰到一種就能直接回傳失敗，這叫提前終止。
      • 「堆疊要存右括號」 —— 不用。右括號用完即丟，只有左括號需要「等待」，所以只有它需要被記住。
      04

      程式架構與說明

      只講流程與分工，不逐行拆解。看懂這一段，你就能自己改這個遊戲。

      整體設計：先算完，再播放

      這個頁面最重要的一個決定是：使用者按「開始」之前，整段過程就已經全部算好了。

      輸入字串 "{[()]}"
      buildSteps(s) 把整串跑完一次
      steps[] 每一格是一個「當下的完整快照」
      畫面只負責把 steps[目前步數] 畫出來

      為什麼這樣設計

      • 前進後退變成加減一 —— 不必為了「倒退」去寫反向操作堆疊的邏輯，那是錯誤最多的地方。
      • 畫面函式變單純 —— 給同一個 step，畫出來一定一樣，不依賴之前發生過什麼。好懂也好除錯。
      • 演算法和畫面完全分離 —— buildSteps 裡沒有半行畫面程式碼，它就是純粹的括號匹配演算法，可以單獨拿去用。
      代價 每一步都存一份堆疊快照，最壞情況記憶體是 O(n²)。教學規模（幾十個字元）完全沒問題，但真實工程不會這樣寫——真實版本只要一個布林值答案，不需要留下過程。

      模組分工

      層主要函式負責什麼
      資料層 buildSteps(s) 唯一真正跑演算法的地方。輸入字串，輸出一整個步驟陣列。
      狀態 S 一個物件裝所有狀態：目前字串、目前第幾步、模式、分數。全站只有這一份。
      畫面層 paintTape / drawArcs
      renderTower / paintAlgo
      paintSay / paintLog      		 各自只讀 steps[S.cur]，畫自己那一塊，彼此不互相呼叫。
      導覽 goto / next / prev
      startPlay / stopPlay      		 只做一件事：改 S.cur，然後呼叫 render()。
      闖關 nextQuizIndex
      renderQuiz / answerQuiz      		 出題、對答案、計分。它不碰演算法，只是「先不給看下一步」而已。
      載入 loadString / loadLevel
      setMode      		 換題目、換模式，重建 steps 並歸零。

      畫面更新的流程

      不管使用者做什麼，路徑都是同一條。這是整個程式最好記的部分：

      使用者操作 按鈕 / 鍵盤 / 答題 / 自動播放
      goto(k) 只改 S.cur 這一個數字
      render()
      paintTape字元顏色
      drawArcs配對弧線
      renderTower堆疊塔
      paintAlgo高亮行
      paintSay說明文字
      paintLog歷程
      重點 六個畫面函式誰都不知道別人存在。要加第七塊畫面，就多寫一個函式掛進 render()，其他一行都不用改。

      核心資料：一個 step 長什麼樣

      整個程式就靠這個物件串起來。每個欄位都是為了餵給某一塊畫面：

      {
  kind:        // start / push / pop / skip / error / done
               // → 決定顏色、徽章文字、歷程標籤
  i:           // 指標在第幾格 → 字元帶的三角形指標
  ch:          // 這一格的字元
  stackBefore: // 動作前的堆疊快照
  stackAfter:  // 動作後的堆疊快照 → 堆疊塔直接畫這個
  match:       // pop 時，配到的左括號在第幾格 → 畫弧線用
  line:        // 演算法要高亮第幾行
  title, msg:  // 說明面板的標題與內文
  why:         // 錯誤種類：empty / mismatch / leftover
}

      注意 stackAfter 是快照不是參考——每一步都複製一份新的陣列。這正是「可以自由倒退」的代價與底氣。
