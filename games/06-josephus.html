Game 06 · Josephus Problem

約瑟夫問題

n 個人圍成一圈報數，數到 k 的人出局，然後從下一個人重新數。你要站哪個位置才能活到最後？這個西元 67 年的求生問題，答案就藏在佇列的兩個基本操作裡。

先押一個位置，再看它到底活不活得下來。

怎麼玩

畫面左邊是圍成一圈的人，右邊是同一群人在佇列裡的排隊順序。兩邊是同一件事的兩種畫法 —— 這正是這個遊戲要你看見的。

  1. 設定人數 n 和報數到 k。
  2. 在「我猜第 □ 號活」押一個位置。被你押的人會有虛線外框。
  3. 按 單步 一次跑一個 dequeue，看清楚每一次「出隊」之後是回到隊尾還是被淘汰。
  4. 看懂之後改按 自動播放，用滑桿調速度。
  5. 猜中了會有提示；沒猜中就換個位置再來。
看這裡 右邊佇列的第一格（橘色）永遠是下一個要報數的人。每按一次單步，這一格就會離開隊伍 —— 然後要嘛排到最後面，要嘛直接消失。

你會學到什麼

  • 佇列的 FIFO 特性 —— 先進先出。從隊頭出、從隊尾進，永遠只碰兩端。
  • 用 dequeue + enqueue 模擬繞圈 —— 這是本頁最重要的一招：「圍成一圈」和「排隊」其實是同一件事。
  • 為什麼不能用 vector.erase(begin()) —— 陣列從頭刪除要搬動所有元素，是 O(n)；佇列的 dequeue 是 O(1)。
  • 兩種解法的取捨 —— 模擬法看得見過程但慢，數學公式快但看不見過程。
  • 遞推公式 J(n) = (J(n−1) + k) mod n —— 為什麼「殺掉一個人之後就是同一個子問題」。
  • k = 2 的二進位規律 —— 一個漂亮到不像真的的結論。
建議順序 先用 n=7、k=3 單步走完一輪（答案是 4 號），對照第 03 段的手算表。再把 k 設成 2，試 n=1 到 8，自己找出規律。

演算法（C++）——玩到哪，亮到哪

O(n·k)

    整份程式逐行白話說明（寫給完全沒學過程式的你）

      這個遊戲跑的程式（完整版）

      把畫面全部拿掉，模擬法就這麼幾行：

      // 模擬法：用佇列
#include <queue>
using namespace std;

int josephus(int n, int k) {
    queue<int> q;
    for (int i = 1; i <= n; i++) q.push(i);
    while (q.size() > 1) {
        for (int i = 0; i < k - 1; i++) {
            q.push(q.front()); q.pop();   // 沒中，回到隊尾
        }
        q.pop();                          // 中了，直接淘汰
    }
    return q.front();
}

// 公式法：更快，但看不見過程
int josephusFast(int n, int k) {
    int r = 0;                            // J(1) = 0
    for (int i = 2; i <= n; i++)
        r = (r + k) % i;
    return r + 1;
}
      03

      這個功能是怎麼做到的

      從「圍成一圈」怎麼變成「排隊」開始講。

      問題定義

      n 個人圍成一圈，編號 1 到 n。從 1 號開始報數 1、2、3…，數到 k 的人出局，接著由他的下一個人重新從 1 開始報，直到只剩一個人。求生還者的編號。

      故事 西元 67 年，猶太史學家 Flavius Josephus 和 40 名同伴被羅馬軍隊困在山洞。同伴決定圍成一圈，每數到 3 的人就自殺，也不投降。約瑟夫不想死，他當場算出「第幾個位置會活到最後」，悄悄站過去 —— 最後他活了下來。你現在玩的，就是他在山洞裡算的東西。

      關鍵洞察：圍成一圈，就是排隊

      圓圈很難用程式表示 —— 沒有開頭也沒有結尾。但只要換個角度就通了：

      關鍵 「輪到你報數，報完沒中，你走到隊伍最後面重新排隊」 —— 從隊伍的角度看，這跟繞一圈回到原位是完全一樣的事。

      一旦這樣看，整個問題就只剩佇列的兩個基本操作：

      圈子裡發生的事佇列的操作結果
      輪到隊頭的人報數dequeue()他離開隊伍
      報的數不是 k，安全enqueue(他)回到隊尾，等下一輪
      報的數正好是 k，出局（什麼都不做）他就這樣消失了

      注意第三列：「出局」在程式裡不需要任何動作。dequeue 出來之後不把他放回去，他就自動不見了。這是這個解法最漂亮的地方。

      演算法

      queue ← [1, 2, 3, ..., n]              // 所有人排成一列

while queue 的長度 > 1:
    重複 k−1 次:
        queue.enqueue(queue.dequeue())  // 報數 1~k−1：出隊，再回隊尾
    out ← queue.dequeue()               // 報數第 k 個：出隊，不放回
    記錄 out 出局

return queue.dequeue()                  // 剩下的就是生還者

      整個演算法只有 dequeue 和 enqueue 兩種操作，沒有搜尋、沒有刪除中間元素、也沒有陣列搬移。

      手算一次：n = 7、k = 3

      佇列由左到右就是排隊順序，最左邊是 front。

      報數出隊的人處置佇列（front → rear）
      ——初始1 2 3 4 5 6 7
      11回隊尾2 3 4 5 6 7 1
      22回隊尾3 4 5 6 7 1 2
      33出局4 5 6 7 1 2
      14回隊尾5 6 7 1 2 4
      25回隊尾6 7 1 2 4 5

      出局順序是 3 → 6 → 2 → 7 → 5 → 1，生還者是 4 號。在上面的遊戲設 n=7、k=3 單步走一遍，對照這張表。

      為什麼一定要用佇列，不能用一般陣列

      用陣列也能做，但「把第一個元素拿掉」這件事在陣列裡很貴 —— 後面所有元素都要往前搬一格。

      做法取出隊頭放回隊尾n = 100000 時
      陣列 vectorerase(begin()) → O(n)push_back() → O(1)慢到不能用
      std::queue（底層是 deque）pop() → O(1)push() → O(1)瞬間完成
      環形佇列front++ → O(1)rear++ → O(1)瞬間完成，且不配置記憶體
      差多少 n = 10 萬時，erase(begin()) 版本和 std::queue 版本的差距超過 一千倍。這不是常數差異，是複雜度差異。

      複雜度

      • 模擬法 O(n·k) —— 每淘汰一個人要做 k 次 dequeue／enqueue，總共淘汰 n−1 個人。
      • 空間 O(n) —— 佇列最多裝 n 個人。
      • 公式法 O(n) —— 見下一塊。快，但看不見過程。

      進階：不用模擬，直接算

      當你只要答案、不要過程時，有一個 O(n) 的遞推公式（這裡先用 0 起算的編號）：

      J(1) = 0
J(n) = ( J(n−1) + k ) mod n

// 答案（改回 1 起算）= J(n) + 1

      為什麼成立

      殺掉第一個人之後，剩下 n−1 個人，這是一模一樣的子問題 —— 只是「從誰開始數」變了。原本從 0 號開始，現在從第 k 號開始。所以只要把子問題的答案整體往後移 k 格，再對 n 取餘數繞回來，就是原問題的答案。

      以 n=7、k=3 驗算：J(1)=0 → J(2)=1 → J(3)=1 → J(4)=0 → J(5)=3 → J(6)=0 → J(7)=3，加 1 得到 4。跟手算表一致。

      彩蛋：k = 2 的二進位規律

      把 k 設成 2，試不同的 n，把生還者記下來：

      n生還者拆解n 的二進位
      112⁰ + 01 → 1
      212¹ + 010 → 01
      332¹ + 111 → 11
      412² + 0100 → 001
      532² + 1101 → 011
      652² + 2110 → 101
      772² + 3111 → 111
      812³ + 01000 → 0001
      公式 把 n 寫成 n = 2m + L（其中 0 ≤ L < 2m），生還者就是 2L + 1。
      更酷的說法：把 n 轉成二進位，把最高位的 1 搬到最右邊，就是答案。
      例：n = 13 = 1101 → 1011 = 11，所以第 11 號生還。上去驗證看看。

      常見誤解

      • 「出局的人要從佇列裡刪掉」 —— 不用。dequeue 出來之後不放回去，他就已經不在佇列裡了。特地去「刪除」反而是多做工。
      • 「要記錄每個人在圈上的位置」 —— 不用。佇列的順序本身就是圈上的相對順序，位置只是畫面上的事。
      • 「k 比人數大就不能玩」 —— 可以。報數會繞好幾圈才數到 k，佇列會轉很多次，結果一樣正確。
      • 「用 vector.erase 也能過」 —— 小 n 確實能過，所以很多人不會發現問題。等到 n 變大就會炸。這是最典型的「答案對但複雜度錯」。

      按下單步 / 自動播放的計時器
      microStep() 真的做一次 dequeue
      直接改動 queue 陣列 沒有存快照

      （本頁）      		 程式短、記憶體小，跟真實實作長得一樣 不能倒退，只能重新開始 參數可調、重跑成本低

      狀態變數

      變數型別負責什麼
      queue陣列唯一的真相來源。還活著的人，順序就是排隊順序。
      outSetSet已出局的編號。只為了畫面把他們畫成灰色，演算法不需要它。
      tick數字目前報到第幾聲。數到 k 就歸零。
      guess數字使用者押的位置。純粹是遊戲元素。
      running / timer—自動播放用。

      注意 outSet 和 guess 是畫面才需要的東西。把它們拿掉，演算法照樣正確 —— 這就是「哪些是演算法、哪些是包裝」的分界線。

      核心：microStep() 的流程

      整個遊戲的心臟只有這一個函式，每次做一件事：

      front ← queue.shift() dequeue，隊頭出隊
      tick 加一，這是他報的數
      tick < kqueue.push(front) 回隊尾
      tick = k不放回，tick 歸零
      render()，並檢查是否只剩一人

      就這樣。整個約瑟夫問題就是這個分岔重複到剩一個人為止。

      畫面層分工

      函式畫什麼怎麼決定樣子
      render()總開關依序叫下面幾塊，每次全部重畫
      drawRing()圓圈上的人用三角函數算座標；顏色看 outSet、queue[0]、guess
      drawQueue()右邊佇列直接把 queue 陣列畫成一排方塊
      drawStats()四個數字從 queue.length、outSet.size 讀
      say() / log()說明與歷程由 microStep 在做決定的當下呼叫
      為什麼全部重畫 每次都把整個圈重新產生一遍，聽起來很浪費，但 n 最多 24，成本可以忽略。用一點效能換掉「局部更新漏改」這類 bug，在教學程式裡是划算的。
