Game 09 · Circular Queue

環形佇列排隊

顧客從 rear 進場、從 front 離場，兩根指標在同一個圓環上追著跑。看清楚「滿了」和「空了」為什麼長得一模一樣、要怎麼分辨，以及 % 這個符號是怎麼把「走到底」變成「繞回去」的。

怎麼玩

畫面上有一個 8 格的圓環：綠色 front 指著「下一個要離場的人」，橘色 rear 指著「下一個進場的人要站的空位」。圓環下面是同一份資料的另一種長相——一條 8 格的陣列。

演示模式

  1. 從上方挑一個關卡（一段進場／離場的劇本），或自己輸入。
  2. 按 下一步 一個操作一個操作走；也可以 自動播放。
  3. 盯著三件事同步變化：圓環上的兩根指標、下方陣列的 F／R 標籤、演算法高亮行。
  4. 特別注意 rear 或 front 從第 7 格跳回第 0 格的那一步——那就是「環形」的全部意義。

闖關模式

  1. 每個操作前先不給答案，由你猜：這次會成功還是失敗？指標會停在哪一格？剩幾個人？
  2. 答對得分，連續答對額外加分；答錯立刻告訴你正確答案和理由。
操作 鍵盤 → 下一步、← 上一步、空白鍵 播放／暫停。

你會學到什麼

  • 佇列＝排隊（FIFO） —— 先進先出：先來的顧客先被服務。enqueue 是進場排到隊尾，dequeue 是隊頭的人離場。
  • front 與 rear 各管一件事 —— front 指下一個離場的人、rear 指下一個空位，兩根指標都只往前走、從不後退。
  • 直線陣列的「假滿」 —— 前面明明空出一排格子，新顧客卻進不來。環形就是為了回收這些格子而生的。
  • % 模運算 —— (7+1) % 8 = 0：一行數學就把陣列的尾巴接回頭，不用搬任何東西。
  • 滿與空的世紀難題 —— front == rear 既可能是空、也可能是滿。用 count 或「犧牲一格」才分得出來。
  • 複雜度 O(1) —— 進場離場都是固定幾個動作；對比「離場就整排往前搬」的 O(n)。
建議順序 先玩「暖身」和「整條填滿」「全部離場」，親眼看到滿和空長得一樣；再玩「繞一圈」盯住 rear 從 7 跳回 0 的瞬間；最後切闖關模式挑戰「魔王」。

    整份程式逐行白話說明（寫給完全沒學過程式的你）

      這個遊戲跑的程式（完整版）

      把教學用的視覺化全部拿掉，環形佇列本體就是這樣——加上三個常見的輔助函式：

      #include <iostream>
using namespace std;

const int N = 8;                       // 排隊區固定 8 格

struct CircularQueue {
    int data[N];                       // 8 個格子
    int front = 0, rear = 0, count = 0;

    bool enqueue(int x) {              // 進場：排到隊尾
        if (count == N) return false;  // 滿了，拒絕，否則會蓋掉別人
        data[rear] = x;
        rear = (rear + 1) % N;         // 走到底就繞回 0 的關鍵一行
        count++;
        return true;
    }
    bool dequeue() {                   // 離場：隊頭的人走掉
        if (count == 0) return false;  // 空的，沒人可走
        front = (front + 1) % N;
        count--;
        return true;
    }
    int  peek()  { return data[front]; } // 看看排最前面的是誰
    bool empty() { return count == 0; }
    bool full()  { return count == N; }
};

      不到三十行。遊戲頁面多出來的幾百行，全部都是為了「讓兩根指標的追逐看得見」——這是教學程式和生產程式的差別。

      03

      這個功能是怎麼做到的

      從「排隊」這個需求，一路走到「為什麼非得把陣列接成環」。

      問題定義

      佇列（queue）就是「排隊」：新來的人排在隊尾（enqueue，進場），輪到的人從隊頭離開（dequeue，離場）。先來的先被服務——這叫先進先出（FIFO，First In First Out）。本關的題目是：用一條「固定 8 格的陣列」把排隊做出來，而且每個動作都要一樣快，不管隊伍多長。

      對 8 格佇列做的事結果原因
      進 3 人，再離場 1 人成功離場的一定是最早進來的 1 號——先進先出
      已有 8 人，再進 1 人失敗count == N，8 格全有人，硬放會蓋掉別人
      空佇列做 dequeue失敗count == 0，沒有人可以離場
      進 8、出 2、再進 2成功rear 繞回第 0、1 格，把離場者用過的格子回收再用

      先破除一個直覺：直線陣列不行

      用一條直線陣列裝排隊，有兩種天真做法，各壞在一個地方。

      • 做法一：有人離場就整排往前搬 —— 隊頭走一個人，後面所有人都往前挪一格。n 個人排隊就要搬 n−1 次，dequeue 變成 O(n)。收銀台每叫一個號，全店的人都要動一次，隊伍一長就慢到不能用。
      • 做法二：不搬，front 往右移就好 —— 快是快了，但 front 走過的格子永遠沒人再用。進 8 個、出 5 個之後，明明只剩 3 個人，rear 卻已經頂到牆——這就是「假滿」：前面空了一大排，新顧客卻進不來。

      「假滿」長這樣（直線陣列、進 8 出 5 之後）：

      格 0格 1格 2格 3格 4格 5格 6格 7rear
      （空） （空） （空） （空） （空） 678 8 → 出界，判「滿」
      關鍵 直線陣列浪費的不是空間本身，是「front 走過的格子回收不了」。要回收，就把尾巴接回頭——讓陣列變成一個環。

      關鍵觀察：% 就是「繞回去」的數學寫法

      想讓「第 7 格的下一格是第 0 格」，不必真的把記憶體折成圓圈——記憶體永遠是直的——一行數學就夠了：

      下一格 = (現在的位置 + 1) % 8

      % 唸作「模運算」（mod），意思是「做除法、只留餘數」。(7+1) % 8：8 ÷ 8 = 1 餘 0，所以下一格是 0。而位置在 0～6 時，加 1 之後還不到 8，除以 8 商 0、餘數就是它自己——完全不受影響。只有「走到底」那一刻，% 才出手把你拉回 0。

      比喻 時鐘就是生活裡的模運算：11 點再過 3 小時，不是 14 點，是 (11+3) % 12 = 2 點。時鐘是 %12，我們的佇列是 %8——環，就是取餘數。

      演算法

      兩根指標、一個計數器，全部只往前走：

      1. enqueue（進場） —— 先檢查 count == N（滿了就拒絕）→ 把人放進 rear 指的格子 → rear = (rear+1) % N → count++。
      2. dequeue（離場） —— 先檢查 count == 0（空的就拒絕）→ front = (front+1) % N → count--。格子裡的舊資料不必清，front 走過去它就「不算數」了。
      3. 任何時候 —— 隊伍裡的人就是「從 front 出發、順時針數 count 個格子」。
      最常漏 順序不能反：一定要先檢查滿、再放人。先放再檢查，就已經把還沒離場的顧客蓋掉了。另一個常漏的是 count++／count--——忘了它，滿空判斷全盤皆錯。

      「滿」和「空」為什麼長得一樣？怎麼分辨？

      空的時候，rear 追上 front，兩根指標疊在同一格；全滿的時候，rear 繞了一整圈，又剛好追上 front。兩個畫面裡 front == rear 一模一樣——光看指標，分不出天堂和地獄。玩「整條填滿」和「全部離場」兩關，可以親眼看到這兩個長得一樣的瞬間。

      怎麼分辨方法 A：多記一個 count（本頁採用）方法 B：犧牲一格
      判「空」count == 0front == rear
      判「滿」count == N(rear + 1) % N == front
      能裝幾人N 人（8 人，一格不浪費）N−1 人（永遠留一格空的當緩衝，滿的時候 rear 停在 front 前一格，兩者就不會相等）
      代價多一個整數變數少一格容量
      都對 兩種解法都正確、都常見。C++ STL 沒有現成的環形佇列，面試最愛考的就是：你知不知道 front == rear 有歧義、你選哪一招破解。

      手算一次（縮小成 N = 4）

      8 格手算太累，縮成 4 格練一次。劇本：進 1、進 2、進 3、出、出、進 4、進 5。考試就是畫這張表——先蓋住右邊自己算。

      複雜度

      • enqueue O(1) —— 放人、指標加一取餘、count 加一：三個固定動作，跟隊伍多長完全無關。
      • dequeue O(1) —— 同樣三個固定動作。對比「搬移法」的 O(n)：一百萬人排隊時，是 3 個動作對上一百萬次搬動。
      • 空間 O(N) —— 開店就把 8 格劃好，有沒有人都占著。「容量固定、絕不搬移、每步一樣快」正是硬體要的確定性——鍵盤緩衝區、網卡的封包佇列、音訊緩衝區，底層全是環形佇列。

      常見誤解

      • 「rear 指著最後一個人」 —— 本頁的 rear 指著「下一個空位」。另一派教科書讓 rear 指最後一個人，初始值和判斷式全都不同。讀任何程式前先確認它用哪種慣例，兩派混用必出 bug。
      • 「front == rear 就是空」 —— 不一定，也可能是全滿。要嘛看 count，要嘛用犧牲一格法保證滿的時候 front 永遠不等於 rear。
      • 「dequeue 要把格子清空」 —— 不必。front 移走後那格自然就「不算在隊伍裡」，下次 enqueue 直接覆蓋。真的去清是多做工（本遊戲畫面上清掉，純粹是為了看得清楚）。
      • 「滿了讓陣列自動變大就好」 —— 那是動態陣列（vector）的玩法。環形佇列的價值恰恰在容量固定、永不搬移；緩衝區寧可拒絕新資料，也不能在中斷處理中途搬記憶體。

      程式架構與說明

      只講流程與分工，不逐行拆解。看懂這一段，你就能自己改這個遊戲。

      整體設計：先算完，再播放

      這個頁面最重要的一個決定是：使用者按「開始」之前，整段劇本就已經全部算好了。

      操作劇本 "++++--++…"（+ 進場、- 離場）
      buildSteps(ops) 把整段劇本跑完一次
      steps[] 每一格是「8 個格子 + 三個數字」的完整快照
      畫面只負責把 steps[目前步數] 畫出來

      為什麼這樣設計

      • 前進後退變成加減一 —— 不必寫「反向 enqueue」這種容易錯的東西，倒帶就是把步數減一。
      • 畫面函式變單純 —— 給同一個 step，畫出來一定一樣，不依賴之前發生過什麼。好懂也好除錯。
      • 演算法和畫面完全分離 —— buildSteps 裡沒有半行畫面程式碼，它就是第 02 段那份 C++ 的 JS 翻譯，可以單獨拿去用。
      代價 每一步都存一份 8 格快照，記憶體是 O(步數 × N)。教學規模（幾十步 × 8 格）完全沒問題，真實工程不會這樣寫——真實版本只需要當下狀態。

      核心資料：一個 step 長什麼樣

      整個程式就靠這個物件串起來。每個欄位都是為了餵給某一塊畫面：

      {

      注意 data 是快照不是參考——每一步都複製一份新陣列。這正是「可以自由倒帶」的代價與底氣。
