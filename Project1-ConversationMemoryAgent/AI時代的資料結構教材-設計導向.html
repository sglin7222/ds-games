然後他們審查代碼、測試、改進。

- 第 1 頁 -

新的教學流程：設計 → AI 實現 → 審查 → 優化

每週 4 個步驟（不涉及基本語法）

第 1 步：理解設計需求（1-2 小時）

你需要回答 3 個問題：

  1. 為什麼需要這個資料結構？
    • 例：Stack - 為了支持「撤回」功能，後進先出
  2. 應該有哪些操作？
    • 例：push、pop、peek、size、is_empty
  3. 時間複雜度應該是多少？
    • 例：push/pop 應該是 O(1)，不能是 O(n)

第 2 步：用 AI 實現代碼（1-2 小時）

如何使用 Claude：

你：「幫我用 Python 實現一個 Stack。
要求：
- 有 push、pop、peek、size、is_empty 5 個方法
- push/pop 的時間複雜度是 O(1)
- 添加完整的文檔字符串」

Claude：[給你完整的代碼]

你：檢查代碼，看是否滿足要求
💡 AI 提示： 不要讓 AI 教你 Python 語法。只讓它寫代碼。你的工作是審查和改進。

第 3 步：測試和審查（1-2 小時）

關鍵問題：

  1. 代碼能跑嗎？ 運行測試
  2. 時間複雜度對嗎？ 分析 push/pop 的操作次數
  3. 有邊界情況嗎？ 空棧、單元素棧
  4. 可以改進嗎？ 是否有冗餘代碼
你：「這個 pop 方法有什麼問題嗎？」

Claude：「如果棧是空的，pop 會拋異常。
應該檢查 is_empty()。」

你：「修改代碼。」

Claude：[修改代碼]

第 4 步：應用和優化（1-2 小時）

真實應用場景：

不只是寫 Stack，而是用 Stack 解決問題：

  1. 場景 1： 實現「撤回功能」
    • 用 Stack 管理編輯歷史
    • 讓 Claude 幫你寫 EditHistory 類
    • 測試撤回功能
  2. 場景 2： 括號匹配
    • 用 Stack 檢查括號是否匹配
    • 分析為什麼 Stack 比列表更合適
- 第 2 頁 -

6 週課程計劃（設計導向）

第 1-2 週：棧（Stack）

🎯 學習目標

  • 理解： 為什麼需要棧？LIFO 原理？什麼時候用？
  • 設計： Stack 應該有哪些操作？時間複雜度是多少？
  • 應用： 用棧實現「撤回」、「括號匹配」、「表達式求值」

📅 每週流程

步驟 你的工作 AI 的工作 時間
1. 理解 回答：為什麼用棧？什麼時候用？ - 30 分鐘
2. 設計 畫出 Stack 的接口（push、pop 等） - 30 分鐘
3. 實現 告訴 Claude：「幫我實現這個 Stack」 寫出完整代碼 30 分鐘
4. 測試 運行測試，檢查時間複雜度 - 30 分鐘
5. 應用 想一個應用場景（如撤回功能） - 30 分鐘
6. 實現應用 讓 AI 寫應用代碼 寫代碼 1 小時
7. 審查優化 分析代碼，問「能改進嗎？」 優化代碼 1 小時

第 2-3 週：佇列（Queue）

🎯 核心問題

  • 為什麼用 deque 而不是列表？ O(1) vs O(n)
  • 什麼時候用佇列？ 消息隊列、任務調度、BFS
  • 怎樣用 AI 實現？ 告訴 Claude「我需要一個支持 O(1) 入隊和出隊的 Queue」

第 3-4 週：雜湊表（Hash Table）

🎯 核心問題

  • 為什麼用雜湊表查詢會很快？ O(1) 時間複雜度
  • 怎樣用在會話管理？ 快速查詢用戶會話
  • 性能對比： 列表 O(n) vs 雜湊表 O(1)

第 4-5 週：設計 AI Agent 系統

🎯 系統設計（不涉及語法）

  • API 設計： 什麼是 REST？應該有哪些端點？
  • 數據流： 用戶輸入 → Agent 處理 → 返回回應
  • 前端設計： 用戶如何與系統交互？

實現流程：

  1. 你設計系統架構圖
  2. 你告訴 Claude：「幫我實現一個 ConversationAgent，要求：[功能列表]」
  3. Claude 給你代碼
  4. 你測試和審查
  5. 如果有問題：「這裡為什麼要這樣做？能改進嗎？」
  6. Claude 解釋和改進

第 5-6 週：集成和優化

🎯 系統集成

  • 前後端通信： 理解 HTTP、JSON
  • 性能測試： 系統能支持多少並發用戶？
  • 代碼審查： 代碼質量如何？
  • 優化： 能改進哪些地方？

考試例子

例 1：理解深度

問：「為什麼在對話系統中用棧管理對話歷史，而不是用列表？」

期望答案：

  • LIFO：最後一條消息最先被撤回
  • O(1) pop：即使有 10000 條消息，撤回也很快
  • 語義明確：Stack 天然表達「後進先出」的概念

例 2：系統設計

問：「設計一個支持 1000 個並發用戶的聊天系統。你會用什麼資料結構來存儲用戶會話？為什麼？」

期望答案：

  • 用雜湊表（字典），key 是 user_id
  • 理由：O(1) 查詢速度，每個查詢都是常數時間
  • 如果用列表：O(n)，1000 個用戶要掃 1000 次

例 3：代碼審查

問：「這段代碼有問題嗎？」

def pop(self):
    return self._items.pop()  # 如果列表是空的會報錯

期望答案：

  • 有問題：沒有檢查空棧
  • 應該：先檢查 is_empty()，再 pop()
  • 或者：讓它拋異常，但要文檔說明
