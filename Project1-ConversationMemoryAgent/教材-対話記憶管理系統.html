通過構建一個具備對話記憶、上下文管理的 AI Agent 系統，深入學習和掌握資料結構在實際應用中的設計與實現。 本專案不僅教授資料結構的理論知識，更重要的是通過實戰開發，理解如何選擇合適的資料結構來解決實際問題。

1.2 核心概念

為什麼選擇「對話記憶管理」作為背景？

核心洞察： 對話系統天然需要使用不同的資料結構來解決不同的問題。 這使得我們可以在一個統一、有趣的應用背景下，學習多種資料結構及其實際應用。
需求 對話系統中的問題 解決方案 資料結構
消息撤回 用戶發送了消息又想撤回，需要「回到上一步」 存儲消息序列，支持反向遍歷 棧（Stack）
任務調度 多個任務要按順序執行，先進先出 任務佇列，保證順序執行 佇列（Queue）
會話查詢 100 個活躍用戶，快速查詢特定用戶會話 用 user_id 直接定位會話 雜湊表

為什麼是「AI 時代」的資料結構？

傳統資料結構課程的問題： 只教理論和經典算法問題（排序、搜尋等），學生不理解「為什麼要學這個」。

本專案的創新： 在 AI Agent 系統的背景下教授資料結構，讓學生親眼看到資料結構如何：

  • 直接解決實際問題
  • 影響系統性能（棧 vs 列表的查詢效率）
  • 支持新型應用（AI Agent 對話系統）

3.2 資料結構設計

棧（ConversationStack）- 對話歷史管理

目的： 存儲和管理對話消息序列

為什麼選擇棧？ 消息撤回需要從最後一條開始移除（LIFO）

push("用戶：你好") push("AI：你好！") push("用戶：告訴我 Python") push("AI：Python 是...") 當用戶點擊「撤回」時： pop() → "AI：Python 是..." (移除) pop() → "用戶：告訴我 Python" (移除)

佇列（TaskQueue）- 任務調度

目的： 管理後台任務，按順序執行

為什麼選擇佇列？ 任務需要按先進先出（FIFO）順序執行

enqueue(task1: "分析用戶輸入") enqueue(task2: "調用 Claude API") enqueue(task3: "存儲結果") 執行順序（自動）： task1 → task2 → task3

雜湊表（SessionCache）- 會話管理

目的： 快速查詢和存儲用戶會話

為什麼選擇雜湊表？ O(1) 時間複雜度快速查詢特定用戶

SessionCache = { "user1": Session(conversation_stack, task_queue), "user2": Session(conversation_stack, task_queue), "user3": Session(conversation_stack, task_queue), ... } 查詢 user2 的會話：O(1)，直接定位！

資料結構的嵌套關係

Session = {
    user_id: str
    conversation_stack: Stack[Message]  ← 存儲對話消息
    task_queue: Queue[Task]              ← 存儲待執行任務
    metadata: dict
}

SessionCache = HashTable[user_id, Session]  ← 快速查詢會話

初始化流程

1. FastAPI 啟動 → 創建 MultiSessionAgent() 和 SessionCache() 2. 用戶請求建立會話 → MultiSessionAgent.create_session() 3. 新會話包含： - ConversationAgent（含 ConversationStack） - 存儲在 SessionCache 中 4. 用戶發送消息 → MultiSessionAgent.generate_response() - 消息推入 ConversationStack - 調用 Claude API - 回應推入 Stack 5. 返回 JSON 響應給前端

4.2 複雜度分析

各個操作的時間複雜度

操作 時間複雜度 空間複雜度 備註
添加用戶消息（Stack.push） O(1) O(n) n = 消息總數
撤回消息（Stack.pop） O(1) - 直接移除
獲取對話歷史 O(n) O(n) 需要遍歷所有消息
查詢會話（HashTable.get） O(1) 平均 - 直接哈希查詢
建立新會話 O(1) O(1) HashTable 插入
刪除會話 O(1) 平均 - HashTable 刪除
列出所有會話 O(m) O(m) m = 活躍會話數

性能分析示例

場景： 系統有 100 個活躍用戶，每個用戶平均 50 條消息

用列表實現 SessionCache：

  • 查詢特定用戶的會話 → O(100) = 掃描全部用戶
  • 100 個這樣的查詢 → O(10,000) 操作

用雜湊表實現 SessionCache：

  • 查詢特定用戶的會話 → O(1) = 直接定位
  • 100 個這樣的查詢 → O(100) 操作

4.3 系統交互分析

多用戶並發場景

時間→ User1: POST /sessions/user1 User2: POST /sessions/user2 ↓ User1 和 User2 的會話 完全獨立，互不影響 User1: POST /messages (user1) User2: POST /messages (user2) ↓ Agent1 處理 User1 Agent2 處理 User2 （並行） ↓ User1: GET /history (user1) → 看到 User1 的對話 User2: GET /history (user2) → 看到 User2 的對話

為什麼能支持並發？

1. 會話隔離： 每個用戶有獨立的 Agent 和 Stack

2. 快速查詢： 雜湊表 O(1) 查詢，不會因為用戶數增多而變慢

3. 無全局狀態： 每個會話獨立操作，不需要鎖定資源

錯誤處理流程

用戶操作 ↓ 前端驗證 ├─ 會話是否存在？ ← 不存在 → 顯示錯誤信息 ├─ 消息是否為空？ ← 為空 → 顯示錯誤信息 └─ 內容格式正確？ ← 不正確 → 顯示錯誤信息 ↓ 發送到後端 ↓ 後端驗證 ├─ 會話 ID 是否有效？ ← 無效 → 返回 404 ├─ 消息內容是否合法？ ← 不合法 → 返回 400 └─ API 密鑰是否正確？ ← 不正確 → 返回 401 ↓ 處理成功 → 返回 200 + 數據 ↓ 前端更新 UI

C. 常見問題解答

Q: 為什麼用 Python deque 而不是列表？

列表的 pop(0) 是 O(n)，因為需要移動所有元素。 deque 的 popleft() 是 O(1)，更高效。

Q: 棧和佇列的區別？

棧：LIFO（後進先出） - 適合撤回、回溯 佇列：FIFO（先進先出） - 適合排隊、調度
